## Is the telemetry usable for a regular developer today?
Honestly: for debugging the platform, yes; for an app developer, only partly, mostly because the app does almost nothing yet.

**Useful today:**
- Following one request from the gateway to the database, with its logs, through the trace ID.
- Seeing why a pod crashed or won't start (pod logs, events, restarts).
- Seeing which network rule blocked something.
- Spotting slow queries.

**Weak today:**
1. **There's almost nothing to look at.** The app only has health checks, so traces, metrics and the Services dashboard are thin. That fixes itself with the first real endpoints (Phase 9).
2. **App logs appear twice:** once through the app's own telemetry, named `todo-backend`, and once as pod logs, named `backend`. That's confusing, so the pod-log copy of apps that already send their own should be dropped.
3. **Inconsistent names across Loki, Prometheus and Tempo** (`todo-backend` vs `backend` vs the pod name). One app label everywhere would make every query and link line up.
4. **No starting point.** A developer doesn't know where to begin. A "Start here" dashboard per app would help: errors, slowest requests, recent restarts, each linking to its traces and logs.
5. **No link from a metric spike to an example trace.** Prometheus can attach the trace ID of a sample request to a metric (called exemplars), so a click on a latency spike opens that request's trace.
6. **Short retention:** Prometheus keeps 2 days and Loki and Tempo are cleared with the cluster. That's fine locally, and Phase 5 sets real retention in Azure.

My suggestion: make 2–5 a short Phase 2 follow-up (part of making D71 actually useful), together with the two MCP reviews. Then grill Phase 2.5 (the sandbox) and Phase 3.
