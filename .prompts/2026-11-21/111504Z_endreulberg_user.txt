  **1) Lima for AI agents (lima-vm.io/docs/examples/ai/, "AI agents")**
  - Stated purpose: "Lima is useful for running AI agents inside a VM, so as to prevent agents from directly reading, writing, or executing the host files."
  - Mount only the project directory (recommended):
    - Lima v2.0+: `limactl start --mount-only .:w` (drop `:w` for read-only)
    - Lima v1.x: `limactl start --set ".mounts=[{\"location\":\"$(pwd)\", \"writable\":true}]"` (set `writable` to `false` for read-only)
  - No host mounts: `limactl start --mount-none template:default`. Plain mode also disables all filesystem mounts ("In plain mode, all filesystem mounts are disabled", config/mount page).
  - Sync instead of live mounts (Lima >= 2.1): `limactl shell --sync . default claude "Add error handling to all functions"`, or `limactl shell --sync . default`. After the run the user is asked "Accept the changes?" with Yes / No / View the changed contents. The instance must be created with `--mount-none` for sync to work.
  - Sync exclusions (Lima >= 2.3): `limactl shell --sync . --sync-exclude .git default`. The flag is repeatable and passed to rsync as `--exclude`. Alternatively a `.limasyncignore` file in the synced directory, which is passed to rsync as `--exclude-from`.
  - Sync requirements: rsync on host and guest; host working dir at least 4 levels deep; no host mounts on the instance; not the wsl2 VM type.
  - Agent install examples: Claude Code is `lima sudo snap install node --classic`, `lima sudo npm install -g @anthropic-ai/claude-code`, `lima claude`. Auth is done "in the first session". The alternative is `export ANTHROPIC_API_KEY...` placed in `~/.bash_profile` via `lima vi "/home/${USER}.linux/.bash_profile"`. Codex uses `OPENAI_API_KEY`, Copilot uses `GH_TOKEN`. Credentials are therefore just env vars in the guest shell profile, with no secret store or host-to-guest credential handling described.
  - Egress restriction and allowlists: I found NO built-in egress filter, domain allowlist, or related config key in the pages I read.   **2) networkOpts.hostLoopback: false (Lima v2.3; config/network/user page)**
  - Default: the host's loopback is reachable from the guest as `host.lima.internal` (host IP 192.168.5.2, guest 192.168.5.15).
  - Config syntax, from the page:
  ```
  networkOpts:
    hostLoopback: false
  ```
  - Set in `lima.yaml`. Only supported with `vmType: vz`, and not with a `user-v2` network.
  - Effect, quoted from the page: connections to host.lima.internal "are refused instead". DNS, outbound connections to other hosts and `limactl shell` keep working. A host service listening on all interfaces is still reachable through the host's LAN address. A host proxy on 127.0.0.1 (e.g. `http_proxy=http://127.0.0.1:3128`) becomes unreachable from the guest.
  - The v2.3 post says that with this setting connections are "refused immediately" and calls it "(VZ only)".
  
  **3) Docker-in-Lima with no host mounts**
  - Docker templates (examples/containers/docker): `limactl start template:docker` (rootless) or `limactl start template:docker-rootful`, then `export DOCKER_HOST=$(limactl list docker --format 'unix://{{.Dir}}/sock/docker.sock')`.
  - The Docker page does not show a `mounts:` setting. The docs I read give no `mounts: []` YAML example, so I cannot confirm that spelling. The documented no-mount method is `limactl start --mount-none` (AI page) or plain mode (its page was not fetched). Use `--mount-none` on a Docker template: `limactl start --mount-none template:docker` is an inference from those two docs, not an example the docs show.
  - Mount defaults (config/mount table): ">= 1.0: 9p for QEMU (on non-Windows), virtiofs for VZ". For vz the docs give this example: `limactl start --vm-type=vz --mount-type=virtiofs`, with `vmType: "vz"` and `mountType: "virtiofs"`. Virtiofs for vz needs macOS 13+.
  - vmType on macOS: vz is the default and the docs say "'vz' has been the default driver for macOS hosts since Lima v1.0". The vz page gives `limactl start --vm-type=vz` and needs macOS 13+.
  - Speed: none of the pages I read states a speed recommendation for macOS. The defaults are vz + virtiofs. I could not verify a "fastest" claim.
  - Caveat: virtiofs is "experimental on Linux hosts". On the krunkit driver, virtiofs "cannot be enforced to be read-only, even when `writable: false` is set".
  
  **4) kind / Kubernetes in Lima (examples/containers/kubernetes)**
  - kind is NOT mentioned. The page covers single-node templates: `template:k8s` (kubeadm), `template:k3s`, `template:k0s`, `template:experimental/rke2`, `template:experimental/u7s`. Example: `export KUBECONFIG=$(limactl list k3s --format '{{.Dir}}/copied-from-guest/kubeconfig.yaml')`.
  - Multi-node: separate VMs on the `lima:user-v2` network (`limactl start --name k8s --network lima:user-v2 template:k8s`). Lima >= 2.0 for k8s, 2.1 for k3s.
  - Interaction to note: `hostLoopback: false` is not supported with `user-v2`, so the multi-node setup and the hostLoopback isolation cannot be combined.
