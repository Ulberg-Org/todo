## What we can learn from it

Seven runs failed, each on a different Azure behaviour that the preview can't see:

| Failure | The behaviour behind it |
|---|---|
| Defender (`Subscription Not Registered`) | each Azure service must be registered once per subscription |
| Defender (`already existing`) | every Defender plan always exists, at the Free tier until switched on |
| The hub's network rule | Azure refuses "deny everything" without a single allowed network |
| The server's admin | a server accepts only one operation at a time |
| The refresh after that | a failed create leaves an entry in Pulumi's state that blocks the next refresh |
| The hub `azure-logs` | Azure created the hub itself, before Pulumi got to it |
| The diagnostic setting | diagnostic settings outlive their resource and reattach to a new one |

**Where I went wrong:**
1. **I researched how to switch things on, not how they behave.** For a new resource type, the important questions are:
   - does it already exist?
   - does Azure create parts of it itself?
   - does it outlive its resource?
   - can it run in parallel?

   I only researched those after something failed.
2. **The PR was too big:** six new Azure features in one go, so every run found the next problem, one at a time.
3. **I proposed fixes before I had evidence,** and you caught me twice. The verification we did at the end (the preview's list checked against Azure) should have happened before every request for a run.
4. **My own `destroy` fallback created orphans:** it deleted the server without its diagnostic setting, which Microsoft explicitly warns against.

**What would prevent it, in order of value:**
1. **An automatic leftovers check in the PR's preview:** for everything the preview will create, ask Azure whether it already exists, with the preview identity's read access. "Already exists" would then fail in the PR, in a minute, not in a `start`.
2. **A four-question checklist per new Azure resource type** (the questions above), answered in the PR.
3. **Smaller increments:** one new resource type per PR when it's something we haven't used before.
4. **`start` with `--continue-on-error`,** so one run shows every independent error.
