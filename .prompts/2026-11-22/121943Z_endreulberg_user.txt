  ## 1. CI on a pull request
  
  Yes, there is an official composite GitHub Action. It is at the repo root, `action.yml`, named "OpenCodeReview PR Review". Use it as `uses: alibaba/open-code-review@main`. Using `npx` is not the documented CI path. The action installs the CLI itself with `npm install -g "@alibaba-group/open-code-review@${OCR_VERSION}"`, where `ocr_version` defaults to `latest`.
  
  Exact example, from `examples/github_actions/ocr-review.yml` (abridged to the review step and triggers; the file also has a concurrency block and an issue_comment PR-context step, which I left out):
  
  ```yaml
  name: OpenCodeReview PR Review
  on:
    pull_request_target:
      types: [opened, synchronize, reopened]
    issue_comment:
      types: [created]
  permissions:
    contents: read
    pull-requests: write
  jobs:
    code-review:
      runs-on: ubuntu-latest
      timeout-minutes: 30
      if: |
        github.event_name == 'pull_request_target'
        || (github.event_name == 'issue_comment' && github.event.issue.pull_request
            && github.event.comment.user.type != 'Bot'
            && (github.event.comment.author_association == 'MEMBER'
                || github.event.comment.author_association == 'OWNER'
                || github.event.comment.author_association == 'COLLABORATOR')
            && (startsWith(github.event.comment.body, '/open-code-review')
                || startsWith(github.event.comment.body, '@open-code-review')))
      steps:
        # (optional issue_comment step resolves base_ref/head_sha via actions/github-script)
        - name: Run OpenCodeReview
          uses: alibaba/open-code-review@main
          with:
            llm_url: ${{ secrets.OCR_LLM_URL }}
            llm_auth_token: ${{ secrets.OCR_LLM_AUTH_TOKEN }}
            llm_model: ${{ vars.OCR_LLM_MODEL }}
            llm_use_anthropic: ${{ vars.OCR_LLM_USE_ANTHROPIC }}
  ```
  
  The README's minimal form is the same step with the four `with:` keys above. For reproducible runs, the README says to pin the action to a full commit SHA and set `ocr_version: 'X.Y.Z'`. The README notes that `ocr_version` must be at least 1.9.6.
  
  Action flow: it checks out with `fetch-depth: 0`, fetches `pull/<N>/head`, computes `git merge-base`, and runs `ocr review --from <merge-base> --to <head> --format json`. It then posts inline comments plus a sticky summary.
  
  ## 2. LLM providers and configuration
  
  The action inputs are `llm_url`, `llm_auth_token`, `llm_model`, `llm_use_anthropic` and `llm_protocol`. They map to env vars as follows:
  - `llm_url` maps to `OCR_LLM_URL`
  - `llm_auth_token` maps to `OCR_LLM_TOKEN`
  - `llm_model` maps to `OCR_LLM_MODEL`
  - `llm_use_anthropic` maps to `OCR_USE_ANTHROPIC`
  - `llm_protocol` maps to `llm.protocol`, with values `anthropic`, `openai` or `openai-responses`. It takes precedence over `llm_use_anthropic`.
  - `llm_auth_header` maps to `OCR_LLM_AUTH_HEADER`. `llm_extra_headers` maps to `OCR_LLM_EXTRA_HEADERS`. `llm_timeout` (default 300) maps to `OCR_LLM_TIMEOUT`.
  
  Anthropic Claude is supported directly. The README says "OpenAI & Anthropic compatible". The action's secrets are `OCR_LLM_URL` (secret) and `OCR_LLM_AUTH_TOKEN` (secret). The variables are `OCR_LLM_MODEL` and `OCR_LLM_USE_ANTHROPIC`, set to `'true'` for Anthropic and `'false'` for OpenAI-compatible. The action's default `llm_extra_body` is `{"thinking": {"type": "disabled"}}`.
  
  Local CLI setup uses `ocr config provider` and `ocr config model`. The README says "Select a built-in provider or add a custom one". I could not read the built-in provider list (docs 404). The config file name was not shown in anything I read.
  
  ## 3. Permissions and token
  
  The example sets `permissions: contents: read, pull-requests: write`. The README says "`GITHUB_TOKEN` is automatically provided by GitHub Actions with the required `pull-requests: write` permission." The action input is `github_token`, which defaults to `${{ github.token }}`, and its description is "GitHub token used to post review comments." Pass a different token through that input, not an env var.
  
  Exception: `resolve_outdated: 'true'` needs `contents: write`. The action says `pull-requests: write` alone returns FORBIDDEN for that operation. The example puts it in a separate job.
  
  ## 4. Where data goes

  ## 5. Rules config and changed-file scope
  
  - Rules file: `.opencodereview/rule.json` in the repo. The action fingerprints it, and OCR loads it whether or not `rule` is set.
  - Custom rules: the action input `rule` takes "Path to a custom rules JSON file passed to `ocr review --rule`." The action warns: "do not point `rule` at a file sourced from the PR branch when secrets are in scope."
  - Changed-file scope: the review is the diff `merge-base..head`. The docs say path filtering lives in Review Rules, but that page did not load, so I cannot confirm the exact syntax.
  - Whole-file review, not diff review: `ocr scan --path <dir-or-file>` (CLI only, not in the action).
