**Q1: yes, it's the common practice.**
- The usual pattern is that the IaC tool (Terraform or Pulumi) installs Argo CD **once**, along with a root Application. From then on Argo CD manages everything, **itself included**, from Git ("app of apps"). Sources: [OneUptime: bootstrap Argo CD with Terraform](https://oneuptime.com/blog/post/2026-02-26-bootstrap-argocd-terraform/view), [Argo CD's own cluster-bootstrapping docs](https://github.com/argoproj/argo-cd/blob/v2.7.1/docs/operator-manual/cluster-bootstrapping.md?plain=1), [Self-managed Argo CD](https://medium.com/devopsturkiye/self-managed-argo-cd-app-of-everything-a226eb100cf0), [GitOps bootstrap of a fresh cluster](https://abd-ulbasit.github.io/bookstore-kubernetes-guide/14-eks-in-production-a-to-z/10-gitops-bootstrap-fresh-cluster/).
- **The known downside is the handoff.** If the IaC tool later changes what Argo CD has taken over, the two fight. The usual cure is the one I suggested: after installing, the stack ignores changes to it. Upgrading Argo CD then happens in Git (`components/argocd`), the same as locally.
- **One limitation:** if something goes wrong with Argo CD's own Application, fixing it means a new `start`. For dev that's cheap.
