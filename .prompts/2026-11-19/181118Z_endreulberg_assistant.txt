❓ **Q27** - **How do the instances share message processing (inbox/outbox)?** Two techniques, for two different jobs:
- **Claiming rows** in the outbox or inbox: `SELECT … FOR UPDATE SKIP LOCKED`. Each instance takes a batch nobody else holds, without waiting and without double processing. This is the standard Postgres queue pattern, and it beats advisory locks for this job.
- **Singleton jobs** (e.g. the 08:00 notification batch from D50): a Postgres **advisory lock**, so exactly one instance runs it, and another takes over if that one dies.

➡️ Both, in the skeleton:
- an outbox table and a worker loop that claims rows with `SKIP LOCKED`;
- a singleton job guarded by an advisory lock;
- each with a test that runs two instances against the same database and proves every message is processed exactly once, and the singleton runs once.
