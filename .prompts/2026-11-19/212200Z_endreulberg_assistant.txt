**Helm and Kustomize, briefly:**
- **Helm:** a package manager for Kubernetes. A *chart* is a set of templated YAML files plus default settings. You install it with your own values (`helm install envoy-gateway --set …`). It's how third-party software like ArgoCD, Envoy Gateway and Loki is distributed.
- **Kustomize:** no templates. You have plain base YAML files, plus per-environment "patches" that change specific fields (e.g. "in prod, replicas: 3"). It's built into `kubectl`.

Both solve "the same thing, slightly different per environment". **Our renderer solves exactly that too**, from `platform.yaml` plus the environment files. So for our own app, Kustomize would be a second layer doing the same job.

❓ **Q14 (refined)** - **Who owns which environment settings?** Two layers:
- **Platform repo, `environments/{local,dev,prod}.yaml`:** what the platform decides, such as cluster sizes, addresses, how to sign in, telemetry endpoints and the signature check (off locally, Q7).
- **App repo, optional `platform.local.yaml`, `platform.dev.yaml`, `platform.prod.yaml`:** what the *app* decides per environment, like hot reload locally, its log level, or more replicas in prod. The schema limits these files to app-level keys, and D48's policy limits still apply, so a `platform.prod.yaml` can't drop below 2 replicas or claim something the platform owns.
